# CI/CD Анализ и Рекомендации для проекта SportMagazine

## 1. Анализ текущей ситуации

### 1.1 Текущая архитектура развертывания

- **Репозиторий:** GitHub (монорепозиторий)
- **Сервер:** Один VPS (185.251.88.214)
- **Структура:**
  - Frontend (Next.js) - отдельный Docker контейнер
  - Backend (Strapi) - отдельный Docker контейнер + PostgreSQL
- **Reverse Proxy:** Nginx
- **Процесс развертывания:** Ручной (SCP + SSH команды)

### 1.2 Текущие проблемы

1. **Ручное развертывание** - требует много времени и подвержено ошибкам
2. **Нет автоматизации** - каждый раз нужно вручную загружать файлы и пересобирать контейнеры
3. **Нет тестирования** - изменения деплоятся без проверки
4. **Нет отката** - сложно вернуться к предыдущей версии
5. **Нет мониторинга** - не видно статуса деплоя

### 1.3 Требования к CI/CD

- Автоматическое развертывание при push в main ветку
- Раздельное развертывание frontend и backend
- Сохранение .env файлов (не коммитятся в репозиторий)
- Минимальная простоя (zero-downtime deployment)
- Возможность отката
- Логирование процесса

## 2. Варианты CI/CD

### Вариант 1: GitHub Actions (РЕКОМЕНДУЕТСЯ) ⭐

**Преимущества:**

- ✅ Бесплатно для публичных репозиториев
- ✅ Интегрирован с GitHub
- ✅ Простая настройка через YAML файлы
- ✅ Хорошая документация и сообщество
- ✅ Не требует дополнительных серверов
- ✅ Поддержка секретов (GitHub Secrets)
- ✅ Автоматические уведомления

**Недостатки:**

- ⚠️ Для приватных репозиториев есть лимиты (2000 минут/месяц бесплатно)
- ⚠️ Требует настройки SSH ключей на сервере

**Сложность настройки:** Низкая
**Стоимость:** Бесплатно (для публичных репозиториев)

### Вариант 2: Простые скрипты деплоя (Git Hooks)

**Преимущества:**

- ✅ Максимально простой
- ✅ Полный контроль
- ✅ Не требует внешних сервисов

**Недостатки:**

- ❌ Нет автоматизации при push
- ❌ Нужно запускать вручную
- ❌ Нет логирования и мониторинга
- ❌ Нет тестирования

**Сложность настройки:** Очень низкая
**Стоимость:** Бесплатно

### Вариант 3: GitLab CI/CD

**Преимущества:**

- ✅ Мощный функционал
- ✅ Хорошая интеграция с GitLab
- ✅ Бесплатно для приватных репозиториев

**Недостатки:**

- ❌ Требует миграции на GitLab
- ❌ Более сложная настройка
- ❌ Избыточно для простого проекта

**Сложность настройки:** Средняя
**Стоимость:** Бесплатно (если использовать GitLab.com)

### Вариант 4: Jenkins

**Преимущества:**

- ✅ Очень гибкий
- ✅ Много плагинов
- ✅ Можно развернуть на своем сервере

**Недостатки:**

- ❌ Требует отдельный сервер или контейнер
- ❌ Сложная настройка
- ❌ Избыточно для одного проекта
- ❌ Требует поддержки

**Сложность настройки:** Высокая
**Стоимость:** Бесплатно (но требует ресурсы сервера)

### Вариант 5: Docker Hub + Watchtower

**Преимущества:**

- ✅ Автоматическое обновление контейнеров
- ✅ Простая настройка

**Недостатки:**

- ❌ Нужно публиковать образы в Docker Hub
- ❌ Меньше контроля над процессом
- ❌ Нет тестирования перед деплоем

**Сложность настройки:** Средняя
**Стоимость:** Бесплатно (для публичных образов)

## 3. Рекомендуемое решение: GitHub Actions

### 3.1 Почему GitHub Actions?

1. **Простота** - настройка через YAML файлы в репозитории
2. **Бесплатно** - для публичных репозиториев неограниченно
3. **Интеграция** - уже используете GitHub
4. **Гибкость** - можно настроить разные workflow для frontend и backend
5. **Безопасность** - секреты хранятся в GitHub Secrets
6. **Мониторинг** - видно статус деплоя прямо в GitHub

### 3.2 Архитектура CI/CD

```
GitHub Push → GitHub Actions → SSH на сервер →
  → Git Pull → Docker Build → Docker Compose Restart
```

### 3.3 Workflow структура

**Для Frontend:**

1. Триггер: push в `main` с изменениями в `frontend/`
2. Проверка кода (lint, type check)
3. Сборка Docker образа (опционально, можно собирать на сервере)
4. SSH подключение к серверу
5. Git pull в папку frontend
6. Пересборка контейнера
7. Перезапуск контейнера
8. Проверка здоровья (health check)

**Для Backend:**

1. Триггер: push в `main` с изменениями в `backendStrapi/`
2. Проверка кода (lint, type check)
3. SSH подключение к серверу
4. Git pull в папку backendStrapi
5. Пересборка контейнера
6. Перезапуск контейнера
7. Проверка здоровья (health check)

### 3.4 Преимущества этого подхода

- ✅ Автоматизация - деплой при каждом push
- ✅ Раздельное развертывание - frontend и backend независимо
- ✅ Безопасность - SSH ключи в GitHub Secrets
- ✅ Логирование - все логи в GitHub Actions
- ✅ Откат - можно откатить через git revert
- ✅ Уведомления - автоматические в GitHub

### 3.5 Необходимые настройки

1. **GitHub Secrets:**

   - `SERVER_HOST` - IP сервера (185.251.88.214)
   - `SERVER_USER` - пользователь (root)
   - `SSH_PRIVATE_KEY` - приватный SSH ключ
   - `SSH_PUBLIC_KEY` - публичный SSH ключ (опционально)

2. **На сервере:**

   - Настроить SSH ключ для GitHub Actions
   - Убедиться, что git pull работает без пароля
   - Проверить права доступа к Docker

3. **В репозитории:**
   - Создать папку `.github/workflows/`
   - Добавить workflow файлы

## 4. Альтернативный простой вариант: Скрипт деплоя

Если GitHub Actions кажется сложным, можно использовать простой скрипт:

### 4.1 Локальный скрипт деплоя

**deploy.sh** (запускается локально):

```bash
#!/bin/bash
# Простой скрипт деплоя

echo "Deploying to server..."

# Загрузить изменения на сервер
ssh root@185.251.88.214 "cd ~/sportmagazine && git pull"

# Пересобрать и перезапустить frontend
ssh root@185.251.88.214 "cd ~/sportmagazine/frontend && docker-compose down && docker-compose build --no-cache && docker-compose up -d"

# Пересобрать и перезапустить backend
ssh root@185.251.88.214 "cd ~/sportmagazine/backendStrapi && docker-compose down && docker-compose build --no-cache && docker-compose up -d"

echo "Deployment complete!"
```

**Преимущества:**

- Очень просто
- Полный контроль
- Можно запускать когда нужно

**Недостатки:**

- Нет автоматизации
- Нужно запускать вручную
- Нет тестирования

## 5. Рекомендация

**Для вашего проекта рекомендую: GitHub Actions**

**Причины:**

1. Уже используете GitHub
2. Бесплатно и просто
3. Автоматизация без дополнительных серверов
4. Хорошая документация
5. Можно начать с простого и расширять

**План внедрения:**

1. Настроить SSH ключи
2. Создать базовый workflow для frontend
3. Создать базовый workflow для backend
4. Протестировать на тестовой ветке
5. Подключить к main ветке

**Если нужна максимальная простота:**

- Использовать локальный скрипт деплоя
- Запускать вручную после каждого важного коммита
